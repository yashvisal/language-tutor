# Launch audit — 2026-09-06

**Verdict: the conversation product is implemented, but this checkout is not ready for a paid public launch.** The main gaps are purchases, authoritative session ownership, production deployment, and operational verification. The five-minute model is a purchase increment, not a fixed session: the worker meters unheld conversation time in seconds, including tutor speech and silence. Study holds are free.

Branch: `phase-8-audit`, based on `phase-7-product-polish` at `d8b5e1c`. No production configuration was changed and nothing was deployed to production. This audit supersedes the older audit where the code has since changed; phase 7 already fixed many earlier issues.

**Scope clarified during implementation:** Yash wants a local manual walkthrough first. Payment, pricing, and billing changes are explicitly deferred; no E2E harness is requested. The billing findings L1–L4 below remain open, and no lease redesign or payment work was implemented. Hosted deployment and its operational gates follow the walkthrough. The development Convex schema/functions were synced so the local app can store language selections; production was not deployed.

## Implemented in this branch

- A language popover in the shared preflight used by the home dialog and direct `/session` visits. Choices: Spanish, French, German, Italian, Portuguese, Japanese, Korean, and Mandarin Chinese. English remains the explanation language.
- The selected language travels through the bounded plan, browser persistence, the Convex session record, signed LiveKit dispatch, and a per-job worker configuration. Every existing voice, transcription, correction, translation, and study consumer receives that configuration. A session does not mutate another job's defaults.
- Historical plans remain compatible. Missing language means Spanish in the frontend; old dispatches retain the worker's configured default. New web dispatches explicitly carry the selected language.
- Changing languages clears the old language's tense/focus choices. Topic and general notes remain editable and optional. Marketing, onboarding, and home copy no longer claim Spanish is the only option.
- Correction/review language annotations follow the current or historical conversation, including popovers. History shows the selected language.
- Transcript joining preserves noun/name capitalization and real words such as German “um” that previously matched an English filler filter. Correction rendering preserves the original whitespace instead of inserting separators inside words or Chinese/Japanese text. Long CJK text can wrap inline.
- Blocked/full browser storage no longer loses the selected language during the home-to-session handoff; an in-memory fallback carries it for that visit.

**Limits:** deterministic conjugation tables are still Spanish-only (`backend/src/conjugation/`). Other languages use the existing model-based vocabulary/phrase review. Language preference is remembered per browser, not synchronized across devices; level remains an account-wide setting. Non-Spanish voice quality has not been established by these automated checks.

## Findings, in launch priority order

### L1 — Blocker: the browser can release a running session's spending lock

Evidence: [`sessions.finish`](../frontend/convex/sessions.ts) writes `endedAt` directly from an authenticated client request. `sessions.start` treats that field as proof that the previous conversation is over. Finishing the database row does not disconnect its LiveKit room or wait for its final debit.

**Reproduced locally with Convex's in-memory test runtime:** create a learner with 600 seconds; start room A; call public `finish(A)` with an empty outcome without a worker final report; start room B; report 400 seconds from each room. Both debits are accepted and the balance becomes **-200 seconds**. This models two workers sharing the original available balance. The browser needs only its own account credentials and room name.

Fix before accepting money: use a server-owned active-session lease/reservation, distinct from the client history outcome. Release it only after authoritative termination/final reconciliation. Tie worker startup/resumption to that reservation, and reject stale room/token reuse. Closing the UI is a request to end, not proof that spending stopped. Cover rapid end/start, delayed final debits, replayed tokens, and concurrent token requests.

### L2 — Blocker: locks and cleanup use session age rather than liveness

Evidence: `sessions.start` only blocks the newest open row while `Date.now() - startedAt < OPEN_SESSION_WINDOW_MS`; [`billing.ts`](../frontend/lib/billing.ts) sets that window to 15 minutes. [`reconcileStale`](../frontend/convex/sessions.ts) closes any open row whose start is over two hours old, without examining recent worker activity.

**Two local reproductions passed:** (1) an unfinished 16-minute-old session permits a second session; (2) an older-than-two-hours session receives a fresh debit and is immediately marked `stale` by reconciliation. Both conflict with unrestricted conversation length and buy-and-continue.

Resolve with L1: renew a worker-owned lease while active and while legitimately held. Reconciliation should expire an abandoned lease, not a long conversation. Check every relevant open reservation, not just the newest row. A heartbeat is not a billable event.

### L3 — Blocker for paid launch: purchases and buy-and-continue are not built

Evidence:

- [`billing-dialog.tsx`](../frontend/components/app-shell/billing-dialog.tsx) disables purchase buttons with “Coming soon”; home does the same at zero balance.
- There is no checkout route, payment webhook, or purchase grant writer. [`http.ts`](../frontend/convex/http.ts) exposes only worker ledger routes and Clerk account deletion.
- [`schema.ts`](../frontend/convex/schema.ts) defines `purchases.minutes`, while the credit ledger uses seconds.
- [`study-overlay.tsx`](../frontend/components/session/study-overlay.tsx) refuses dismissal at zero; [`out-of-minutes.tsx`](../frontend/components/session/out-of-minutes.tsx) offers home. The worker already supports rereading balance on resume, but the client cannot complete the purchase/resume loop.

Required implementation: choose the payment rail; create checkout from a server-owned pack/price catalog; verify payment webhooks; grant seconds atomically and idempotently by payment identifier; handle asynchronous success/failure, refunds, replay, and duplicate/out-of-order events. A checkout redirect must not grant entitlement. Keep an in-session purchase from destroying the room, then explicitly retry resume after the ledger confirms the grant. Migrate or compatibly extend the purchase unit before deploying writers.

Current displayed packs are **5/$1.99, 20/$5.99, 60/$16.99**, with **600 free signup seconds**, all in [`billing.ts`](../frontend/lib/billing.ts). These are existing product placeholders, not prices validated by this audit. `users.deleteByClerkId` must also acquire a deliberate purchase-retention/deletion policy when purchases gain a writer.

### L4 — High: missing learner metadata bypasses the production metering guard

Evidence: [`agent._open_ledger`](../backend/src/agent.py) returns `meta.balance_s` immediately when `user_id` is missing, before checking `allow_unmetered`. This contradicts the module/readme claim that anonymous jobs require the explicit development escape hatch.

**Executed locally without external calls:** `_open_ledger(None, TutorConfig(tutor_env="production", allow_unmetered=False), JobMetadata(), None)` returns **600**, permitting an unbilled default session. The normal web token route supplies the learner id; this is a production dispatch/configuration failure path, not a demonstrated anonymous web endpoint exploit.

Require complete billing metadata for production jobs; anonymous development jobs should require the explicit development flag. Test absent, malformed, and partial dispatch metadata as well as normal web dispatch.

### L5 — High: deployment and observability are still a plan

Evidence: [`phase-8-launch.md`](phases/phase-8-launch.md) contains the uncompleted production checklist. There is no checked-in worker Dockerfile/LiveKit deployment manifest or application Sentry integration. Existing logging and CI are useful, but do not prove production health.

Before the first public link:

1. Reconcile/merge the phase-7 base and this branch through the intended review flow.
2. Provision production Clerk domain/auth settings, Convex JWT template, the worker/ledger M2M machines and scopes, and the signed `user.deleted` webhook. Verify bot protection and email verification in the actual production instance.
3. Configure production Convex identity/verification variables and deploy its schema/functions. Use distinct development and production resources.
4. Build and deploy the worker with production ledger/M2M/LiveKit/model credentials, **`TUTOR_ENV=production`**, and no unmetered bypass. Pin the runtime, lockfile install, startup command, and any required model downloads in the deploy artifact.
5. Deploy the frontend against that compatible schema and worker. **For this language change, schema → worker → frontend is the safe rollout order**: an old worker ignores the new selection and would still speak its default language.
6. Add server/client/worker exception reporting and alerting for failed dispatch, silent tutor, model failure, failed debit/summary, webhook failures, and negative balances. Scrub learner text and credentials. Record a stable session identifier for correlation.
7. Verify model access using the production API project; defaults are `gpt-realtime-2.1`, `gpt-live-transcribe`, and `gpt-5.6-luna` in [`config.py`](../backend/src/config.py). A local build does not establish those production entitlements or quotas.
8. Load-test expected concurrent rooms, idle/prewarm behavior, reconnects, and scale-down. Have a rollback procedure that does not strand active sessions or mix ledgers.

Production account state, DNS, provider quotas, and live deployment configuration were **not inspected**. These are verification gates, not assertions that no hosted deployment exists.

### L7 — Launch gate: legal/support copy is explicitly unfinished

[`terms/page.tsx`](../frontend/app/terms/page.tsx) and [`privacy/page.tsx`](../frontend/app/privacy/page.tsx) retain draft markers and “to set” values for contact, governing law, minimum age, payment provider, and refunds. ### L8 — Before paid launch: validate economics and metering copy

[`usage.py`](../backend/src/usage.py) now receives auxiliary usage from analyzer, Ask, Review, translation, goal extraction, and summary. The older comments saying most calls are missing are stale. However, one set of text/audio prices is used regardless of the configured model, and text prices are explicitly marked unverified. LiveKit, hosting, payment fees, support/refunds, and free-signup conversion are not part of that model-cost estimate.

Reconcile several representative sessions against provider usage, including long sessions and heavily used free study holds, before setting pack prices. Set spend alerts and a public-beta signup exposure limit. The 12-starts/hour guard is per account; it does not by itself prevent many-account signup abuse. Do not describe the clock as voice-activity-only: it runs throughout an unheld conversation after the first tutor audio, not just while the learner is speaking.

### L9 — Next: persistence and scalability

- [`users.secondsFor`](../frontend/convex/users.ts) collects the user's entire credit ledger for every balance. Periodic debit entries make this grow continuously. Use a transactionally maintained balance plus the append-only audit ledger, or a bounded checkpoint design, before heavy sustained usage.
- The browser can overwrite history's `outcome.secondsTalked` even though it cannot directly change the money ledger. Use worker-billed time for claims such as “that's what you were charged for.” See `sessions.finish` and [`session-summary.tsx`](../frontend/components/session/session-summary.tsx).
- Transcript storage is intentionally bounded to the most recent 200 turns with per-turn caps. That tradeoff matters more now that conversations have no fixed length. Do not promise an unlimited complete transcript.
- Deletion is batched and signed-webhook driven, which is good. Test account deletion during a live room and token expiry to make sure late work cannot revive deleted state. A worker already holds its budget; deletion is not an immediate room shutdown mechanism.

### L10 — Before enabling all languages publicly: actual conversation QA

The configuration path is parameterized and regression-tested, but that does not certify speech recognition, turn detection, or coaching quality. Test each offered language with code-switching to English, pauses, corrections in the middle of a word, Japanese/Chinese wrapping, and translation selection. Check the native labels and language annotations with a screen reader. Spanish-only conjugation tables and the shared level should be intentional product limitations.

Browser automation was unavailable: both default-browser lookup and in-app-browser creation reported no available browser. No visual/keyboard browser pass or live microphone/model conversation was completed. The popover uses the existing Base UI primitive and standard keyboard-operable buttons; its rendering, focus return, nested-dialog interaction, and dark-mode layout still need browser verification.

## What already works and should not be rebuilt

- Clerk-gated routes and server-side token creation; server-generated room/participant identity; bounded session plans; balance gate before issuing tokens.
- Signed/scoped M2M verification, serialized cumulative debits, per-job idempotency references, periodic reporting, and a debit failure ceiling.
- Meter start on first tutor audio, free holds, near-zero warning, zero-balance hold, and the backend balance-refresh/resume seam.
- Stored summaries/review/transcript, ownership checks on history, signed account-deletion webhooks, and batched deletion.
- Frontend/backend CI, runtime/lockfile declarations, security response headers, and a successful local production build.

These are useful foundations. The session-lock defects above remain despite the existing happy-path and ledger tests.

## Shortest credible route to launch

1. Fix L1/L2 together as a server-owned session reservation, and close L4's missing-metadata path. Turn the audit reproductions into tests that expect refusal.
2. Implement and exercise checkout, verified credit grants, refunds, and same-room buy-and-continue in test mode.
3. Triage dependencies; add observability and spending alerts; finalize prices, free grant, support, and draft copy.
4. Deploy the production identity/database/worker/frontend stack with explicit environment isolation.
5. Run the following acceptance pass on the deployed stack, then open a small beta before broader paid acquisition.

Acceptance pass:

- Fresh signup → chosen language → tutor speaks → talk one minute → end → authoritative debit matches visible balance and history.
- Change language, return later, open old history: each conversation retains its own language.
- Pause to read/Ask/translate: no seconds charged; resume naturally.
- Denied microphone, failed dispatch, silent model, lost ledger, dropped network, closed tab, and killed worker: visible recovery and reconciled balances.
- Two tabs, client-forged finish, delayed teardown, expired/reused token, 20-minute conversation, and conversation over two hours: never two spenders sharing one reservation.
- Buy a pack; replay and reorder payment events; refund it: exactly the correct grant/reversal.
- Reach zero → buy while held → resume the same room after confirmed credit.
- Delete an account during and after a session; replay deletion webhook; verify records and operational cleanup.
- Keyboard-only and narrow-screen/dark-mode checks, plus a real conversation in every publicly offered language.

The remaining work is concrete engineering and launch verification. It is more than attaching a payment button, but it does not require redesigning the conversation product.
